# ADR 0019: the browser renders the PDF and the DOCX, the Worker only generates

**Status:** accepted (2026-11-04, fix of M26 in production; CSP hashes and the 5 ms CPU budget added the same day). Amends ADR 0017 §7–8 (rendering in the Worker, rendering on first download).

## Context

In production `GET /api/documents/<key>/v1/cv.pdf` answered Cloudflare error 1102, « Worker exceeded resource limits ». `renderAll` (`worker/src/render.js`) lays the CV out to fill one page: every variant at three type sizes, each a full `PDFDocument.create` + font embedding + `save`. That is seconds of CPU; the Workers Free plan allows **10 ms** a request, and `wrangler dev` does not enforce it. The documents cron was killed in the middle of `renderReady` too, which left rows `running` for good, and the 36 ready versions never got their files. Read from D1 the same day (80 rows): 36 `ready` without files, 15 `running` stuck since 2026-11-02, 29 `failed` of which 23 from the validator (`headline_techs` 7, `profile_chronology` 7, `unknown_name` 5, one each of `invalid_json`, `invented_skill`, `too_long`, `unsourced_tool`), 6 `offer_gone`, none `api_error` nor `render_error`: the cut never shows as an « Échec », it shows as a stuck row.

## Decision

1. **The browser renders.** The same `render.js` (pure: values in, bytes out) is shipped with the dashboard as `assets/render.js`, with its three bare imports rewritten to the UMD globals (`render.browser_renderer`). Its libraries come as browser builds copied by `job-match dashboard` from the Worker's npm install (`site/vendor/`: `pdf-lib.min.js`, `fontkit.umd.min.js`, `fflate.js`; the ESM builds import `pako`, which has no ESM build, so no import map), and the two Inter TTFs go to `site/fonts/`. All are fetched on the first click only, same origin, and kept for the session. CSP: `script-src 'self'` plus the sha256 of each of the page's eight inline scripts (`render.script_hash`), no `'unsafe-inline'` (2026-11-04): an inline script that reached the markup would not run. A click on « ⬇ PDF » / « ⬇ DOCX » fetches the version's bundle, renders the one file asked for and saves it through a blob link named by the template (`CV_Prénom_Nom_Entreprise.pdf`, `Lettre_…`, `Cover_letter_…`). Alternatives: Workers Paid (5 $/month for 30 s of CPU, for one user's downloads), a Durable Object or a Container (the same CPU limit or more moving parts), committing 1.3 MB of minified vendor JS to a public repo (the copy at build time costs nothing more: `npm ci --prefix worker` already runs before the deploy).
2. **`GET /api/documents/<key>/v<n>/content.json`** answers `{content, master, contact}` from R2 (`loadBundle`: the version's `content.json`, `master/cv_master.json`, `master/contact.json`), behind Access, `no-store`, 404 when the version is not ready or a sheet is missing. The contact details leave the Worker to my own browser and nowhere else; `data.json` still carries none. The file routes and `downloadDocument` are gone; `renderReady`, `renderRow`, `loadSheets`, `fileRow`, `fonts.js` and the wrangler `Data` rule for `.ttf` are deleted; pdf-lib, fontkit and fflate are devDependencies (the Node tests and the site build). The `*_key` columns stay in D1 unused: no destructive migration, and `scripts/docs-smoke.mjs` still writes them locally.
3. **Stuck rows and the one automatic retry.** At the start of every pass `requeueStuck` puts back to `pending` the rows `running` for more than `STUCK_MINUTES` (15) and `retryCutOff` requeues once the `failed` rows whose code is in `AUTO_RETRY_CODES` (`api_error`: a 5xx, a 408, an unreadable payload or a network error), marking `documents.auto_retried = 1` (migration 0008). A validator code is never retried by itself: that is « Regénérer » after a look at the code, which the table shows in the badge's tooltip. `document_runs.counters` gains `requeued` and `auto_retried`.
4. **Tests.** Node: the content route (shape, 404s, 401, `no-store`), the requeue and the single retry, a static walk of the Worker's imports (no renderer, no PDF library, no font reachable from `index.js`), and `cpu.test.mjs`: every route of `index.js`'s header and the documents pass under **5 ms of CPU a call**, the mean of 20 calls after one warm-up call (`process.cpuUsage`, user + system, network waits excluded; the mean because Windows ticks `cpuUsage` by 15.6 ms). Half the plan's limit, ten times a D1 + JSON route, a hundredth of a render. **In production, after each deploy:** Cloudflare dashboard → Workers & Pages → `job-match` → Metrics → « CPU time »: P50 / P99 / P999 under 10 ms, and no 1102 under « Errors » (`wrangler tail` shows no CPU figure). Python: `write_site` ships the renderer, the vendor files and the fonts, the rewrite refuses an unknown import, the CSP; Playwright: « ⬇ PDF » saves `CV_Mohamed_Chacrone_Initech.pdf` with the `%PDF-` magic from a mocked `content.json`, the only API call, no `.pdf`/`.docx` path requested; the DOCX likewise; a 404 on the bundle gives a toast and leaves the link usable.

## Consequences

- The Worker's CPU per request is back to D1 + JSON. Downloading costs the browser one to three seconds the first time (1.3 MB of scripts, then the layout search), nothing server-side.
- The deployed site holds the renderer and the libraries: 1.4 MB more of static assets behind Access; nothing of it is personal.
- The first pass after the deploy requeues the 15 stuck rows (within the budget, five a pass); the 36 ready versions are downloadable at once.
- `files` disappears from `GET /api/applications` and `GET /api/documents/:key`: ready means downloadable, nothing else to report.
