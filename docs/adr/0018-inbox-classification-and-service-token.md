# ADR 0018: recruiter replies classified by the Worker, n8n as the client

**Status:** accepted (2026-11-02, M27). Extends ADR 0012 (tracking in D1), ADR 0016 §12 (what the AI may do: emails written by the AI stay out; emails *read* by it come in) and ADR 0009 (Access in front of everything).

## Context

Once an application is « Envoyée », the answer arrives by email: an interview slot, a refusal, an acknowledgement, a request for documents. Today I move the card by hand and often late. n8n already reads my mailbox; what it lacks is somewhere to send each email and something to ask for the follow-ups that are due. The constraints are CLAUDE.md's: the Worker is the only backend, external content is untrusted, nothing personal is stored or logged beyond what the feature needs, the core keeps working without it.

## Decision

1. **An Access service token, scoped by name and by route.** n8n calls the Worker with a Cloudflare Access service token (Client ID + Secret in n8n's credentials); Access turns it into a JWT whose `common_name` is the token's **Client ID** (`<hex>.access`, not its display name) and which carries no `email`. `auth.js principalOf` accepts such a JWT only when its `common_name` equals the Worker **secret** `ACCESS_SERVICE_CN` (`wrangler secret put`, like `CF_ACCESS_AUD`: `wrangler.jsonc` is public and the Client ID is half of the credential), and `handleApi` lets it reach `POST /api/inbox` and `GET /api/followups/due` only (403 elsewhere). My own login (an `email` claim) keeps every route. The same-origin check stays for browser calls and is skipped for the service token: it is not browser-borne, so CSRF does not apply, and n8n sends no `Origin`. Alternatives: a shared bearer secret (one more secret to rotate, outside Access's audit), a second Worker (two deploys for one database).
2. **`POST /api/inbox {message_id, from, subject, date, text}`** (`worker/src/inbox.js`), idempotent by `message_id` (a known id answers 200 with the stored state, no model call). The text is cut to 4 000 characters before anything else; only the sender's domain and the first 200 characters of the subject are stored; the body never reaches D1 nor a log line. Haiku (`claude-haiku-5-5`, the rerank's model and API version, strict `json_schema`, `effort: low`) receives one cached system block (the rules and my « Envoyée » applications as `{application_key, company, title, sent_on}`, joined from D1 and the deployed `data.json`) and the email in `<email>` tags, and answers `{type, confidence, interview_at, application_key, reason}`. `validateInboxVerdict` refuses any key outside the candidates and any date that is not a real day. With `confidence ≥ 0.85` (`CONFIDENCE_THRESHOLD`, `settings.yaml ai.inbox_confidence`) and a type `entretien` or `refus` with a key, `applyVerdict` moves the application (`interview` + `interview_at`, or `rejected`; the pending follow-up is dropped) and the item is `applied`; otherwise the item is `to_confirm`. An AI failure, a spent credit, no sent application, no key or the daily cap all park the email `to_confirm` too: nothing is lost, and the dashboard asks me. One log line: `inbox <state> kind=<kind> ai=<outcome>`.
3. **D1 migration 0007:** `inbox_items(message_id PK, received_at, sender_domain, subject ≤ 200, kind, confidence, interview_at, proposed_key, state ∈ applied|to_confirm|corrected|ignored, applied_key, applied_at, ai_outcome, created_at)` and `applications.interview_at`. The mirror does not carry them (the dashboard reads D1 live, `ai-report` does not need them).
4. **`GET /api/followups/due`:** the `applied` applications whose `follow_up_at` is today or earlier, oldest first, with the offer's title, company and URL from `data.json` (null when the offer is gone). n8n turns it into a reminder; the Worker sends no email.
5. **Dashboard.** A « Réponses à confirmer (N) » block on top of Candidatures lists the parked items (kind, confidence, date, subject, sender domain, the proposed offer or « Candidature inconnue »): Valider (`PUT /api/inbox/:id {action: confirm}`, off when an interview or refusal has no application), Corriger (the application among the sent ones first, the kind, the date; `{action: correct, application_key, kind, interview_at}`), Ignorer. The Worker answers the item and the application it changed, which replaces the card. The record panel shows « Réponses reçues » (every reply attached to the offer) and the Suivi form gains « Entretien le »; the Kanban card reads « Entretien le dd/mm ». The logic is in `tracking.js` (`inboxSummary`, `inboxHistoryFor`, `inboxTargets`, `confidenceText`), Node-tested; the DOM in the browser tests.
6. **Budget.** Billed calls (HTTP 200: ok, invalid or refused) go to `ai_usage` under the Haiku model, like the rerank. The inbox has its own daily cap, `AI_INBOX_DAILY_LIMIT` (50, `settings.yaml ai.inbox_daily_limit`), counted on `inbox_items` rows with a billed outcome that day, so a burst of newsletters cannot eat the rerank's cap nor the reverse.

## Cost

About 1 500 input tokens (1 000 of them cached) and 60 output tokens per email: under $0.001 a call, $0.05 a month at fifty emails a day at most.

## Consequences

- An Access **Service Auth** policy must exist on the dashboard application; the token's Client ID is the Worker secret `ACCESS_SERVICE_CN` and, with the Client Secret, n8n's credential. Neither is in the repo.
- `interview_at` is the first application column absent from the SQLite mirror; `calibrate` and `ai-report` never read it.
- The validator trusts Haiku's `confidence`; the 0.85 threshold is a knob, and every automatic move is visible in the record panel's history to be undone by hand.
